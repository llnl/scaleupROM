## 2026-10-12 - Inventory the existing parallel Poisson path

### Summary

Completed the read-only code-path audit for the first runnable candidate. The
`examples/poisson_parallel` directory is an input/configuration package; it does
not define a separate executable. It uses `build/bin/main`, component topology,
distributed `HypreParMatrix` assembly, and distributed MUMPS when run with more
than one rank and `solver/direct_solve: true`.

The supplied `array.8.yml` defaults to ROM mode. For an FOM baseline it must be
run with `main/use_rom=false`. The supplied sampling input is not the baseline
because its workflow distributes independent samples among ranks rather than
making ranks cooperate on one physical solve.

### Files changed

- No production source changed.
- Generated the example's build-tree HDF5 configurations by running its existing
  `setup_poisson.sh` script.
- Updated this progress entry with the verified call path and current blocker.

### Design and implementation details

The FOM call path is:

```text
bin/main.cpp: main
  -> InputParser and main/mode=single_run
  -> main_workflow.cpp: SingleRun
  -> InitSolver -> PoissonSolver
  -> MultiBlockSolver -> ComponentTopologyHandler and rank load balance
  -> PoissonSolver::InitVariables
  -> BuildRHSOperators / SetupRHSBCOperators / AssembleRHS
  -> BuildDomainOperators / SetupDomainBCOperators
  -> PoissonSolver::AssembleOperator
  -> PoissonSolver::CreateHypreParMatrix when MPI size > 1
  -> PoissonSolver::SetupMUMPSSolverParallel
  -> PoissonSolver::Solve -> distributed MUMPSSolver::Mult
  -> SaveSolution / SaveVisualization
```

Owned subdomains provide local matrix rows and local RHS/solution entries. Stored
neighbor subdomains supply interface columns. `CreateHypreParMatrix()` separates
owned columns into Hypre's diagonal block and remote columns into its off-diagonal
block and column map.

The current iterative Poisson branch is not multi-rank capable: it asserts that
the serial monolithic matrix exists and constructs `CGSolver(MPI_COMM_SELF)`.
Therefore distributed MUMPS is the correct first validation path, not merely a
fallback selected without inspecting the code.

## 2026-10-12 - Run Poisson FOM baseline and isolate two workflow defects

### Summary

Generated the parallel Poisson configurations and ran `array.8.yml` as a FOM by
overriding its default ROM setting. The one-rank FOM completes when ROM-only
system output is disabled. The two-rank FOM reaches distributed matrix assembly
but both ranks segfault in `PoissonSolver::CreateHypreParMatrix()`.

No production fix has been made. This is the first observed failure in the
distributed FOM path and is the appropriate point to decide how much effort to
put into spatial FOM parallelism versus first validating the existing parallel
ROM workflow.

### Files changed

- No production source changed.
- `build/examples/poisson_parallel/configs`: generated by the supplied setup
  script; these are build-tree artifacts.
- Full core files from both ranks were inspected in place.
- This progress entry records the results and proposed next steps.

### Design and implementation details

The example input `array.8.yml` is not a self-contained FOM input:

- `main/use_rom` defaults to `true`, but its required basis and reduced-operator
  artifacts are not included;
- `model_reduction/save_linear_system/enabled` also defaults to `true` and is
  meaningful only for a ROM run; and
- `visualization/enabled` can be disabled to keep the baseline focused.

The working one-rank FOM override was:

```text
main/use_rom=false
visualization/enabled=false
model_reduction/save_linear_system/enabled=false
```

The first segfault was caused by the FOM override leaving ROM-system output
enabled. `SingleRun()` leaves its `rom` pointer null in FOM mode, then calls
`rom->SaveRomSystem()` based only on the output option. The production correction
should guard that operation with `test->UseRom()` or reject the invalid option
combination clearly. Disabling the option allowed the one-rank FOM to complete.

For the two-rank run, both full cores have the same stack:

```text
PoissonSolver::CreateHypreParMatrix()
  -> PoissonSolver::AssembleOperator()
  -> SingleRun()
  -> main()
```

`CreateHypreParMatrix()` indexes `neighbors[j - numSubLoc]` for stored remote
subdomains. `MultiBlockSolver::neighbors` is populated during parallel ROM
assembly, but not on the FOM path. The smallest proposed shared correction is to
populate it from `TopologyHandler` after topology export in the
`MultiBlockSolver` constructor. That proposal must be tested rather than recorded
as a completed fix. It is relevant to Poisson and Stokes because both distributed
FOM matrix builders consume this neighbor ordering.

The experiment also clarified two different kinds of useful parallelism:

- **sample/ensemble parallelism:** each rank or scheduler job performs a separate
  serial FOM training sample;
- **spatial parallelism:** several ranks cooperate on one distributed FOM matrix
  and solve.

The current sampling workflow is naturally suited to the first. The branch also
contains an incomplete implementation of the second. Spatial FOM parallelism is
valuable because FOM samples are normally much more expensive than online ROM
solves, especially when one sample is too large for one rank. A later production
workflow can combine both by assigning several ranks per sample and running
multiple sample groups concurrently.

### Validation

- The setup script succeeded when run from
  `build/examples/poisson_parallel`, its documented working directory.
- Running it from the source directory fails because `generate_configs.py` uses a
  build-tree-relative Python import path; this is an example usability issue.
- The one-rank FOM completed successfully with all three overrides above. Exact
  numerical output was not retained in this entry and must be captured in the
  next comparison run.
- The two-rank FOM failed consistently on both ranks during distributed Hypre
  matrix construction, before distributed MUMPS setup or solve.
- GDB inspected two approximately 65 MB cores and identified the common function
  and call stack. Earlier 12 KB cores were unusable because of the core-size
  limit.

### Open issues and next steps

There are two reasonable near-term tracks.

**Track A: finish the first distributed FOM baseline.**

1. Add a focused assertion or diagnostic proving that the stored ghost count and
   `neighbors.Size()` agree before Hypre assembly.
2. Populate the existing neighbor list on the FOM path using the smallest shared
   change.
3. Rebuild and rerun the same two-rank Poisson case.
4. Compare one- and two-rank solution norms or errors, not only exit status.
5. Run on four ranks, then exercise Stokes, which uses the same neighbor mapping.
6. After distributed MUMPS validates assembly, implement or repair a distributed
   iterative path. The current Poisson iterative code uses a serial monolithic
   matrix and `MPI_COMM_SELF`.

The first correction is small. The total effort is not yet known because the run
has not progressed beyond matrix construction; further assembly, ownership,
solver, or solution-transfer defects may appear. Distributed iterative solving is
a separate, larger increment.

**Track B: validate the intended parallel ROM workflow first.**

1. Run serial FOM sampling or independent FOM samples across ranks/jobs.
2. Train component bases from the snapshots.
3. build reusable component, boundary, and port ROM operators;
4. run `array.8.yml` with `main/use_rom=true` and
   `model_reduction/hypre_matrix=yes`; and
5. verify distributed ROM matrix ownership and compare with a one-rank ROM.

The branch provides the sampling input and final ROM input, but not a complete
parallel-example chain for training bases and building all required artifacts.
That workflow must be assembled from the existing general Poisson inputs and
verified step by step.

The recommended next action is Track A's focused neighbor-invariant test and
small fix, because it directly targets the expensive FOM capability and the
failure is already localized. Stop and reassess effort after the two-rank run
reaches either the solve or the next concrete blocker. Track B remains useful for
separately characterizing what the branch already supports for online ROMs.

## 2026-10-02 - Add explicit owned and stored mappings

### Summary

Added explicit global-to-owned, global-to-stored, and stored-to-global mapping
APIs, together with a focused MPI test of their distinct semantics.

### Files changed

- `test/test_topol.cpp`: tests ownership, stored-index round trips, and exact ghost
  counts for the fixed two-rank 2D fixture.
- `include/topology_handler.hpp`: added the three explicit mapping functions.

### Design and implementation details

Owned lookup consults only `g2l_sub`. Stored lookup first checks owned entries and
then `nghb2loc`. Reverse stored lookup uses `local_subs`, whose owned prefix is
followed by ghost entries during component-topology setup. The legacy ambiguous
mapping methods and all callers remain unchanged in this increment.

For the fixed 2-by-2 fixture, two MPI ranks each own one adjacent pair and store
the other pair as ghosts. The test therefore requires exactly two ghost meshes per
rank and four ghost copies collectively, catching missing and extraneous ghosts.

## 2026-10-02 - Pair global ghost IDs with owner ranks

### Summary

Added explicit, paired arrays containing each locally stored ghost's global
subdomain ID and owning MPI rank.

### Files changed

- `test/test_topol.cpp`: verifies exact ghost global IDs and owners for the fixed
  two-rank fixture.
- `include/topology_handler.hpp`: stores and exposes the paired ghost metadata.
- `src/topology_handler.cpp`: constructs both arrays together during neighbor
  discovery.

### Design and implementation details

`GetGhostGlobalSubdomains()` explicitly identifies its values as global IDs.
`GetGhostOwnerRanks()` returns the corresponding communicator ranks. Both arrays
are populated in the same loop over the existing ordered `subNeighbors` set, so
entry `i` in each array describes the same ghost. Existing mesh construction still
uses `subNeighbors`, preserving its order and behavior.

### Validation

- Expected pre-change result: compilation fails because the two ghost metadata
  accessors are absent. No user-run pre-change output was reported.
- `git diff --check` passed after implementation.
- User-reported result: all prescribed parallel topology tests passed with two
  MPI ranks.

### Open issues and next steps

The ghost metadata increment is complete. The next change makes the tested ghost
global-ID array the central source for stored-mesh construction.

Two architectural issues are explicitly deferred for later review:

- The distributed FOM currently clones each neighboring component's complete
  mesh and finite-element space. Port assembly only uses the boundary-element
  pairs in `InterfaceInfo` and their adjacent volume elements (`Elem1No`). A
  future design should evaluate replacing full ghost subdomains with an
  interface-element representation containing the required geometry,
  transformations, orientations, and trace DOF maps. This is an optimization and
  communication-design change, not part of the current topology API increment.
- Advection intentionally has no port/interface flux in the formulation used by
  the paper underlying this code. `AdvDiffSolver` applies MFEM's
  `ConvectionIntegrator` as a subdomain volume term without integrating the
  advection term by parts, so no advective boundary term is introduced. The
  shared `InterfaceForm` therefore contains only
  `InterfaceDGDiffusionIntegrator`. For future advection-dominated applications,
  the formulation could instead integrate advection by parts and add a suitable
  port numerical flux, such as an upwind flux with explicit inflow treatment.
  That would deliberately extend the mathematical formulation rather than fix
  the current implementation, and would require stability, conservation,
  convergence, and serial/MPI equivalence tests.

### Main-branch audit

The local `main` branch was checked at commit `77fef84` without switching branches.
It contains a newer `AdvDiffSolver` flow-solver interface, including selectable
Stokes or steady Navier-Stokes flow generation and a separate flow discretization
order. It uses the same intentional volume-only advection formulation: no
advection/convection interface integrator or upwind port flux exists on that
branch. Its Poisson-derived port operator remains
`InterfaceDGDiffusionIntegrator`, and it has no ghost-element representation.
The parallel branch's stored-neighbor topology machinery is also absent from
`main`.

Validation was a read-only comparison using `git grep`, `git show`, and `git diff`
against the local `main`; no build was required for this documentation-only audit.
